# 实施计划：双方案视频拆解 POC

日期：2026-09-23。轻量本机工作台已实施并启动；三个内部测试 MP4 的 A/B 完整工作流已运行，接口、Schema、输入证据和导出检查通过。模型对业务内容的语义正确性仍待人工评审。

## 1. 实施原则

- 一个本机工作台、一套共享抽帧、一款指定模型、两条独立工作流。
- 优先把真实结果跑通并可核对，界面只承载上传、播放、并排阅读和导出。
- 每个阶段保留可演示结果，避免直到最后才拿真实视频调用模型。
- 根据真实失败调整；不提前引入 Agent 框架、镜头检测、模型训练和分布式基础设施。
- 需求与规则以 [PRODUCT_BASELINE](PRODUCT_BASELINE.md) 和 [POC_SPEC](POC_SPEC.md) 为准。

## 3. 按依赖顺序实施

以下工时只是单开发者集中工作的初步估计，接口稳定、依赖安装顺利且素材就绪时约 7–11 小时；不是交付时间保证。若有效工作时间不足，采用第 6 节的保留 / 延后顺序。

### S0 — 启动环境与正式输出探针（约 0.5–1 小时）

- 建立 Python 应用、依赖文件和启动说明。
- 配置 FFmpeg / FFprobe、模型环境变量、数据目录。
- 对正式 SingleFrameOutput / SequenceOutput 做最小请求，验证输出长度、JSON 字段及 SDK/HTTP 参数。
- 完成 image-user-message、thinking disabled、temperature、JSON 模式兼容检查。

交付：本机服务可启动，模型适配器及配置可用；既有模型探针证据保留。

状态：本机依赖和服务启动已检查；完整 P10 / P20 / P30 链路已对三条内部测试视频实际运行。结果只验证调用与契约可用，不代表模型内容已经业务验收。

### S1 — 上传、抽帧、FrameSet（约 1–1.5 小时）

- 实现视频上传、元数据探测、统一解码与按秒选帧。
- 处理旋转，保持图片比例，生成共享 JPEG 与 manifest。
- 页面显示原视频和带时间戳的图片清单，点击跳转播放位置。
- 计算视频与图片哈希；处理非整秒、单帧视频、不可解码文件。

状态：三个 MP4 全片按 1.25、2.50、1.50 秒间隔分别抽取 17、20、17 帧；FrameSet 与图片读取已核验。模型无法可靠提供的源 PTS 仍记录为 null。

状态：三个内部素材的帧数、顺序、图片哈希和名义时间戳通过程序核对；首轮发现 `fps round=near` 在非整数采样率下少输出一帧，已改为向上取整并重跑。业务人员仍需回看片样检查重要画面覆盖。

### S2 — 共用模型层与 A 工作流（约 1.5–2 小时）

- 实现模型请求、usage / latency 记录、有限重试和契约校验。
- 实现 P10，每帧独立请求、并发上限 3，按 manifest 排序归档。
- 实现 P30，接收 A 文字记录，生成 FinalReport。
- 输出原始与规范化结果、每帧状态、分支状态。

状态：三条素材 A 均完成逐帧结果与报告；有效帧数为 17/17、20/20、17/17。三处重复 evidence ID 采用确定性去重并在调用记录留痕，其余结构通过 Schema。

验收：E02（A）、E03（A）、E05、E07；相邻图绝不出现在 A 的单帧请求中。

### S3 — B 联合工作流与对照任务（约 1–1.5 小时）

- 实现有序 text/image 对；使用相同帧文件、字段和共同模型参数。
- 实现 P20、Frame/Interval 校验，再复用 P30。
- 实现 Comparison 配置冻结、分支隔离、运行顺序和新建重跑。
- 检查一组失败后另一组仍能执行。

状态：三条素材 B 均完成逐帧分析、16/19/16 个相邻区间及报告；有序图片哈希与共享 FrameSet 顺序一致，正常调用数均为 2。

验收：E02（B）、E03（B）、E04、E09；比较 manifest 证明条件一致。

### S4 — 最小工作台、评审和导出（约 1.5–2 小时）

- 逐帧与区间的 A/B 左右对照；unknown / inferred 明确显示。
- 全片主题、风格、内容结构和提示词对照；复制与下载。
- 展示真实状态、阶段进度、耗时、token 和重试；不虚构 B 逐帧进度。
- 业务评分、偏好和证据备注另存；原结果不可被评价覆盖。
- 支持历史结果读取和 JSON/Markdown 导出。

状态：任务、历史、图片/视频读取、业务评审保存、JSON/Markdown 导出均已通过接口核对；实际页面视觉与内容可读性仍建议会议前由业务人员走查。

验收：E06、E08、E10；图片和报告按同一编号对齐。

### S5 — 真实素材检查与会议准备（约 1.5–3 小时，含人工审阅）

- 首先跑一条十秒左右真实视频，及时修正字段缺失和输出截断。
- 若时间允许，覆盖 5 条不同类型的短片，并对 1–2 条重复一次观察稳定性。
- 验证品牌目标只影响改编输出。
- 保留错误与未知项，整理错误发生在采样、视觉识别、时序归纳还是提示词编写。
- 形成会议演示顺序、真实报告快照和待讨论结论。

状态：已用三条内部测试 MP4 完成技术闭环；尚未用业务标注评估准确性，也未测品牌改编质量、跨运行稳定性或生成视频效果。

验收：所有 E 条件有结果记录；业务维度允许不达标，不能因此美化模型输出。

## 4. 必要验证清单

验证围绕会影响实验真实性和会议可用性的风险，不给简单样板代码堆测试。

| 检查 | 方法 | 合格条件 |
|---|---|---|
| 抽帧正确性 | 自制含时间标识短片＋人工回看 | 数量、顺序、方向、时间基准符合约定 |
| A/B 输入隔离 | 捕获请求构造结果 | A 每次一图、B 所有有序图片；A 无历史上下文 |
| 共用实验条件 | 对比两个分支 manifest | 同 FrameSet 哈希、同模型参数、同汇总模板 |
| 契约验证 | 正常及缺帧 / 重复 / 伪造 ID / 错时间样例 | 错误不通过，unknown 不被自动改成肯定结果 |
| 网络与格式错误 | 模型适配器故障注入 | 429、超时、截断、非法 JSON 均有限重试并留痕 |
| 部分失败 | A 一帧失败、B 缺帧 | 状态 partial / failed，不展示伪完整结果 |
| 重启和重跑 | 运行中重启；重复创建任务 | interrupted 可见；新结果不覆盖旧结果 |
| 用量统计 | 与供应商响应对比 | 计入全部调用与重试，不重复计缓存 token |
| 真实模型闭环 | 同一个真实视频运行 A/B | 最终结果可查看和导出；内容质量单独评审 |
| 界面与导出一致性 | 页面回看＋检查导出 | 时间戳、字段、模型版本和原始结果一致 |

本轮设计文件的 JSON Schema / 示例格式检查独立记录，不替代上表中的应用验证。

## 5. 会议评审安排

建议使用一条普通样本、一条差异明显的样本、一条失败或不确定样本，避免只展示最好看的结果。

演示顺序：

1. 播放原视频，业务先说希望被识别出的 3–5 个关键特征。
2. 展示实际抽帧，判断重要画面是否已进入模型输入。
3. 看 A/B 的逐帧描述，找具体正确项与错误项。
4. 看相邻区间，检查主体运动、运镜和切镜有没有混淆。
5. 看全片总结和提示词，判断是否保留了业务认为重要的表达方式。
6. 最后看耗时、调用数量和 token；记录偏好及原因。

会议输出允许为：A 更适合 / B 更适合 / 各有优势 / 两者均不足 / 样本不足。后续动作应对应失败原因：

| 发现 | 后续候选 |
|---|---|
| 关键镜头根本没抽到 | 同样本加密采样，再决定是否做镜头切分 |
| 图中明显信息识别错误 | 调整提示词或对照另一模型 |
| 单帧正确但时序错误 | 检查联合输入、时间标识与时序规则 |
| 分析正确但提示词空泛 | 调整共同汇总 / 提示词模板 |
| 提示词合理但成片效果差 | 进入后续视频生成模型验证，当前 POC 尚未覆盖 |

## 6. 时间不足时的范围取舍

必须保留：两条真实工作流、同一抽帧输入、逐帧 / 整体对照、错误可见、原始结果落盘和报告导出。

可延后：复杂评分表（先备注＋偏好）、盲评显示切换、批量上传、多视频统计、可调抽帧参数的 UI、高级样式和品牌改编的细化编辑。

模型接口临时不可用时，可展示之前已经成功生成的真实报告，注明生成时间；若没有真实结果，诚实演示已完成的流程和阻塞点，不用假数据声称方案已跑通。

## 7. 实施完成时的交接

- 更新基线的 Implemented / Verified 状态及证据位置。
- 提供实际启动命令、已安装的依赖版本、FFmpeg 路径和数据目录。
- 列明真实样本数量、调用模板版本、运行日期、工程检查结果和业务待判断事项。
- 记录发现的主要错误类型及对应原视频时间，不替业务预先判定方案胜负。
